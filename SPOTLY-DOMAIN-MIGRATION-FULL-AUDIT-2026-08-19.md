# Spotly Domain Migration — Full Production Audit

**Audit date:** 19 August 2026  
**Repository:** Spotly Web Platform 5.5.3 + current Business/Marketplace/Driver/Lottie/subdomain work  
**Scope:** Customer, Business, Driver, Staff, Admin, authentication, navigation, notifications, payments, PWA, SEO, Firebase, Vercel and legacy-route compatibility

---

## 1. Executive conclusion

The move from one path-based Spotly origin to five dedicated product origins affected much more than redirects.

The target architecture is:

```text
spotlyafrica.com                 Spotly customer / marketing / Marketplace
business.spotlyafrica.com        Spotly Business
driver.spotlyafrica.com          Spotly Driver
staff.spotlyafrica.com           Spotly Staff
admin.spotlyafrica.com           Spotly Admin
```

The initial domain migration successfully redirected users between products, but several surrounding systems still behaved as if every portal lived under path prefixes such as `/business`, `/driver`, `/staff` and `/admin`. The visible symptom was sidebar state not following the clean subdomain route. The deeper audit found additional cross-origin issues involving route collisions, sign-in return paths, stale sibling authentication, theme persistence, notification links, payment callbacks, crawler behavior, PWA start URLs and legacy redirect churn.

The current source now treats **clean product-local paths as canonical** and the old path-prefixed URLs as compatibility redirects only.

# 4. Root cause of the sidebar-selection defect

The workspace sidebar highlight was previously allowed to depend on page-provided `activeSection` values and route definitions that still came from the old path model.

That is fragile after a hostname rewrite because the browser-visible route may be:

```text
/staff
```

while the underlying App Router tree still renders:

```text
/business/staff
```

The fixed `PortalShell` now derives active navigation from the actual current route using:

```text
usePathname()
→ normalizePortalPath()
→ activePortalNavigationId()
```

It uses the page-provided section only as a fallback.

This means the sidebar, collapsed sidebar, mobile bottom navigation and “More” sheet all use one resolved active section.

---

# 5. Critical route collision found: Business `/staff`

This was one of the most important hidden bugs in the domain migration.

On:

```text
business.spotlyafrica.com/staff
```

`/staff` means:

> the Team / Staff section **inside the selected Business**

It must not mean:

```text
staff.spotlyafrica.com/
```

A generic “first segment equals another product name” parser could not distinguish those meanings.

The source now has centralized `PORTAL_LOCAL_SECTIONS`. Product-local interpretation happens **before** cross-product legacy interpretation.

Therefore:

```text
Business /staff     stays Business Team
Business /support   stays Business Support
Driver /support     stays Driver Safety & Support
Admin /staff        can still mean the Staff product when explicitly used
Apex /staff         redirects to staff.spotlyafrica.com
```

The edge proxy and client navigation use the same centralized definition so they cannot disagree.

---

# 6. Root links no longer escape to the customer product

Another migration bug was the interpretation of `/`.

On a product domain, `/` must mean the current product's root:

```text
business.spotlyafrica.com/
driver.spotlyafrica.com/
staff.spotlyafrica.com/
admin.spotlyafrica.com/
```

It must not be treated as a request to return to the customer site.

`resolveSpotlyHref("/", { currentPortal })` now always keeps `/` local.

Explicit customer destinations such as `/account`, `/marketplace`, `/claim`, `/drive`, `/privacy`, `/terms` and `/payment` still move to the customer origin when invoked from another product.

# 7. Workspace switcher

The top-left workspace switcher now goes directly to the canonical product origins:

```text
Spotly          → https://spotlyafrica.com
Spotly Business → https://business.spotlyafrica.com
Spotly Driver   → https://driver.spotlyafrica.com
Spotly Staff    → https://staff.spotlyafrica.com
Spotly Admin    → https://admin.spotlyafrica.com
```

The switcher no longer routes through apex `/business`, `/driver`, `/staff` or `/admin` compatibility URLs.

Workspace availability still derives from actual access state:

- Customer is always available.
- Business requires Business access/membership.
- Driver requires Driver profile/application/access.
- Staff requires Staff profile/access.
- Admin requires actual Admin authority.
- Super Admin receives all workspaces.

# 8. Sign-in return-path preservation

A less obvious domain regression existed for unauthenticated deep links.

Previously, opening:

```text
business.spotlyafrica.com/staff?business=abc
```

while signed out could send the user to login and then return only to the Business root.

`AuthGate` now records the exact clean current path and query string in `next=`.

The flow is now:

```text
business.spotlyafrica.com/staff?business=abc
→ business.spotlyafrica.com/login?portal=business&next=%2Fstaff%3Fbusiness%3Dabc
→ sign in / SSO bootstrap
→ business.spotlyafrica.com/staff?business=abc
```

The destination validator rejects non-Spotly absolute URLs and unsafe schemes.

# 9. Cross-subdomain Firebase SSO

## Why normal Firebase persistence is not sufficient

Firebase browser persistence uses origin-specific browser storage. A Firebase user signed into:

```text
business.spotlyafrica.com
```

cannot be read directly by JavaScript on:

```text
admin.spotlyafrica.com
```

because those are separate origins.

The correct Spotly solution is now a parent-domain server session bridge.

## Implemented flow

```text
1. User signs into Firebase on any Spotly origin
2. Browser sends Firebase ID token to /api/auth/session
3. Firebase Admin verifies the ID token
4. Server issues Secure HttpOnly spotly_session cookie for .spotlyafrica.com
5. User opens another Spotly product
6. That product calls /api/auth/session/bootstrap
7. Firebase Admin verifies the shared session cookie
8. Server issues a Firebase custom token
9. The new origin signs in with the custom token
10. Existing Firestore/Auth security continues normally
```

The shared cookie is never exposed to JavaScript.

# 10. Global browser sign-out hardening

A deep SSO audit found an important stale-session edge case.

If Business and Admin each had a local Firebase session and the user signed out in Business, an unopened Admin tab could retain its local Firebase persistence. If it later found no parent-domain session, naïve logic could treat that as “SSO not initialized” and recreate the shared cookie from the stale Admin session.

That would effectively resurrect the session the user had just signed out of.

The fix adds:

```text
spotly_signed_out
```

as a Secure HttpOnly parent-domain marker.

On explicit logout:

```text
spotly_session    → cleared
spotly_signed_out → set
local Firebase    → signed out
```

A sibling origin seeing `signed_out` or an expired shared session signs out its stale local Firebase session instead of reseeding SSO.

The sign-out marker lasts up to one year in this browser, but a legitimate new login immediately clears it. This prevents a rarely visited sibling origin from resurrecting a stale session weeks or months later.

Active portals reconcile the shared session:

- on browser focus;
- when the tab becomes visible;
- every five minutes while active.

This also lets a sibling portal react to account switching or shared-session expiry without requiring a hard reload.

# 11. Theme persistence across product domains

LocalStorage is also origin-specific.

Without additional work, a user could set Dark mode in Business and then open Admin and unexpectedly return to a different theme.

Theme state now mirrors to the non-sensitive parent-domain preference cookie:

```text
spotly_theme
Domain=.spotlyafrica.com
SameSite=Lax
Secure in production
```

Each product keeps its own local copy for fast rendering, but reconciles the shared preference on focus/visibility. This makes light/dark/system mode feel like one Spotly account rather than five unrelated sites.

Sidebar collapsed/expanded state remains product-local intentionally because different portals have different navigation density.

# 12. Legacy redirect compatibility versus canonical generation

Old links remain supported:

```text
spotlyafrica.com/business/staff
business.spotlyafrica.com/business/staff
```

both resolve to:

```text
business.spotlyafrica.com/staff
```

But the application itself should not keep generating those legacy URLs.

The audit therefore cleaned major client and server-generated destinations, including:

- workspace switcher;
- User menu settings;
- Business customer preview;
- Business claims and claim status;
- Driver active/support links;
- Staff links from Admin People Operations;
- Admin support-view links;
- Business delivery and kiosk links;
- notification destinations;
- Admin review queue destinations;
- Driver review destinations;
- Business launch/review email destinations.

A new source regression test scans client navigation to ensure direct JSX/imperative legacy portal URLs are not reintroduced.

Business code can still pass old-form strings into `businessHref(...)` because that helper exists specifically as a compatibility normalizer and emits clean Business-local paths.

# 13. Notifications, email and push

Every notification has an owning workspace.

The canonical dispatcher now stores canonical URLs at write time:

```text
Business event → business.spotlyafrica.com/...
Driver event   → driver.spotlyafrica.com/...
Staff event    → staff.spotlyafrica.com/...
Admin event    → admin.spotlyafrica.com/...
Customer event → spotlyafrica.com/...
```

The global notification tray also canonicalizes old stored URLs when opened, so historic notifications remain usable.

Transactional email buttons use the same canonicalizer.

FCM push data and `webpush.fcmOptions.link` use the same canonical workspace URL.

Push-token records include:

```text
workspace
origin
```

so Business alerts prefer a Business-origin push token instead of opening the alert from whatever Spotly origin registered most recently.

# 14. Firebase Messaging service worker

Each product origin registers its own same-origin `/firebase-messaging-sw.js`, which is required because service workers cannot control sibling origins.

This is intentional.

The shared notification payload contains an absolute canonical Spotly URL, so a background notification opened from a Business service worker can still correctly open Driver/Admin/Customer when the notification belongs elsewhere.

# 15. Payment callback origin

The same backend now serves multiple product domains. A payment provider callback must not accidentally inherit whichever product hostname initiated a shared API call.

Paynow callback and customer return URLs are now pinned to the customer apex in production:

```text
https://spotlyafrica.com/api/payments/paynow/result
https://spotlyafrica.com/payment/return
```

This protects payment configuration from the workspace-domain split and keeps customer payment state on the customer product.

# 16. Kiosk domain and runtime audit

The canonical Business kiosk routes are:

```text
business.spotlyafrica.com/kiosk
business.spotlyafrica.com/kiosk/live
```

`KioskLive` recognizes both the clean URL and the old `/business/kiosk/live` form for compatibility.

The live kiosk continues to bypass the Business owner's normal AuthGate and uses its revocable device-scoped credential.

The production runtime audit also found a recent `/api/kiosk/lookup` Zod validation error. A short/empty lookup code is now handled with `safeParse()` and a friendly HTTP 400 response instead of becoming a production 500.

# 17. Business context and selected-business query state

The Business context no longer assumes the browser path begins with `/business/`.

Business identity and selected `?business=<id>` context continue to work on clean routes such as:

```text
/branches?business=...
/staff?business=...
/delivery?business=...
```

Business route generation uses `businessHref()` to preserve selected-business query context while emitting the clean path.

This is important because a domain migration is incomplete if navigation works but silently loses which Business/location the operator was using.

# 18. Admin queue and Staff cross-product links

Admin queue pages are internal Admin routes and now stay on clean Admin paths.

Admin People Operations intentionally links to the **Staff product** using absolute canonical Staff URLs rather than relative `/staff/...` links. This avoids ambiguity with Business's local `/staff` route.

Queue-derived sidebar state also maps to the operational Admin section that owns the queue rather than always highlighting the generic Control Centre.

# 19. SEO and crawler behavior

Dedicated Business, Driver, Staff and Admin hosts are private application surfaces.

They now:

- expose workspace-specific `robots.txt` that disallows crawling;
- redirect product-domain `/sitemap.xml` to the customer sitemap;
- set `robots.index = false` and `robots.follow = false` in product layouts;
- use hostname-aware PWA manifests;
- keep `start_url` and `scope` as `/` on the current product origin.

The customer root remains the public indexable product/marketing origin.

---

# 20. Apex / www redirect ownership

Application code intentionally **does not** decide between:

```text
www.spotlyafrica.com
spotlyafrica.com
```

Vercel must own that canonical redirect in exactly one direction.

Recommended:

```text
www.spotlyafrica.com → spotlyafrica.com
```

Do not also configure:

```text
spotlyafrica.com → www.spotlyafrica.com
```

at the same time.

The previous `ERR_TOO_MANY_REDIRECTS` failure occurred because domain and application canonicalization can conflict when more than one layer tries to own this decision.

# 22. PWA / installation behavior

A user can install Business, Driver, Staff or Admin from its own hostname and the installed app opens at that product's `/` rather than at an old prefixed path.

The domain split therefore remains compatible with future “app-like” web installation without requiring separate codebases.

# 23. Security review of shared-domain cookies

The sensitive authentication cookie is:

- HttpOnly;
- Secure in production;
- SameSite=Lax;
- parent-domain scoped only for Spotly production;
- verified server-side with Firebase Admin;
- inaccessible to front-end JavaScript.

Shared auth endpoints reject non-Spotly origins in production and use `Cache-Control: no-store`.

The theme cookie is intentionally non-HttpOnly because it is a non-sensitive presentation preference that must be readable by each sibling product.

---

# 24. Remaining intentional origin-local browser state

Not every browser state should be shared.

Examples intentionally left origin/device-specific:

- Kiosk device enrollment: tied to the physical shared tablet.
- Sidebar collapsed state: portal-specific navigation preference.
- Customer basket: customer product only.
- temporary modal/form state: page-specific.
- service-worker registration: must be origin-specific by browser security design.

The domain migration should not create a parent-domain cookie for every piece of UI state.

# 28. Final judgment

The domain split should now behave as **one Spotly account with five intentional products**, rather than one application that happens to redirect between five hostnames.

The distinction matters:

```text
Domain routing
+ navigation state
+ business/location context
+ shared authentication
+ global sign-out
+ notification destinations
+ email/push links
+ payment return URLs
+ PWA behavior
+ crawler behavior
+ user preferences
+ legacy compatibility
```

all have to agree on the same product ownership model.

That model is now centralized and covered by regression tests instead of being repeated ad hoc throughout the UI.
